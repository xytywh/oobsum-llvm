CSA Summary 2.0 · 调研包 v3.15 · 2026-10-13 · 开发环境

在自己的 Windows 电脑上开发：WSL2 + 上游 llvm-project 14.0.0

公司电脑不能做开发，所以代码在自己的电脑上写、编、测，再带去公司编进 BXPlugin、用 bxen 跑业务代码。 第一天装好 Ubuntu 22.04 自带的 clang 14 就能开工；从 GitHub 源码编一份带断言的 clang 可以挂机并行。本地和公司用的是同一份 checker 源码： 本地编成插件，公司走 Checkers.td 注册。每一步脚本都在沙箱里实际跑过。

§1

本地环境与公司环境是什么关系

公司 本地（WSL） 一致吗
LLVM/Clang /usr1/llvm-project-14/cmake-build-release，clang 14.0.0 ~/llvm-project-14/cmake-build-release，GitHub llvmorg-14.0.0（提交 329fda39）；或 Ubuntu 22.04 的 clang-14（同为 14.0.0文档） 版本一致；公司那份是否改过，看 fork-facts.sh 第 3 节
CSA 宿主 xir 内嵌 / 搬移的 CSA（xir/llvm_ast/StaticAnalyzer），可能有定制 上游 clang 14.0.0 的 CSA 未知——fork-facts.sh 第 6 节给出差异计数
checker 注册 Checkers.td 包块 + 源码 CMakeLists.txt，make -j16 日常：插件（-DOOBSUM_PLUGIN_BUILD，clang -cc1 -load）；带去之前：本地预演 Checkers.td 注册（§4.4） 同一份源码两种注册方式，探针已验证
运行 bxen -exec_mode=onlySa … -checker=rb.enhance.… "-extra_args=…" cc1-run.sh -checker=rb.enhance.… 文件.c（clang -cc1 -analyze，同样带 -analyzer-max-loop 3） checker 名、-analyzer-config 写法一致；bxen 另外加载的 config.ini / 函数指针配置本地没有
目标 ABI 业务代码是 aarch64_be + ILP32（4 字节指针、大端） 上游 clang 14 不支持 aarch64 ILP32：aarch64_be-linux-gnu_ilp32 仍按 8 字节指针算，-mabi=ilp32 报 unknown target ABI实测数据；本地近似用 TRIPLE=armebv7-linux-gnueabi（4 字节指针 + 大端） 结构体偏移只能在公司确认（探针 R2）
代码与数据 业务代码、全量 compile_commands.json 只有我们自己的代码和 67 个用例；业务代码不出公司

本地测得到的：checker 逻辑、FIR / 摘要 / 判定、67 个用例与 104 份摘要的对照、注册方式。 只有公司测得到的：xir 的 CSA 定制带来的差异、bxen 的参数与配置、ILP32 布局、业务代码上的告警与性能。

§2

Windows 这边（一次性）

2.1 装 WSL2 与 Ubuntu 22.04

管理员身份打开 PowerShell：

wsl --install -d Ubuntu-22.04      # 第一次装 WSL 会要求重启；重启后自动打开 Ubuntu，设用户名和密码
wsl -l -v                          # 应显示 Ubuntu-22.04 ... VERSION 2
wsl --update                       # 升到最新的 WSL

为什么是 22.04 而不是默认的 24.04：22.04 的 gcc 11 直接编 LLVM 14；Ubuntu 22.04 的 clang-14 包正好是 14.0.0（1:14.0.0-1ubuntu1.1文档）， 与公司一致。24.04 也能用：gcc 13 编 LLVM 14 有两个头文件少 #include <cstdint>，30-build-llvm.sh 会自动打补丁实测数据； 它的 clang-14 包是 14.0.6（同一大版本，API 相同）。

2.2 给 WSL 分配资源

把 devenv/wslconfig.example 复制成 C:\Users\<你>\.wslconfig，按电脑改 memory、processors、swap，然后 wsl --shutdown 再打开 Ubuntu。 WSL2 默认只用物理内存的一半；编 LLVM 每个编译进程约 1–1.5 GB，链接 clang（lld）约 2–3 GB。

2.3 磁盘

WSL 的系统盘是一个 VHDX 文件，默认在 C 盘。整套实测只占约 3 GB（源码含 .git 1.6 GB + 构建目录 1.0 GB + ccache 0.14 GB）实测数据； 算上 apt 包、以后可能再建一个不开断言的构建目录、日常文件，留 15 GB 以上就够。 （这是 Release 构建；带调试信息的 Debug 构建要大一个数量级，这里不推荐。）C 盘紧张就挪到别的盘文档：

wsl --shutdown
wsl --manage Ubuntu-22.04 --move D:\WSL\Ubuntu-22.04     # 较新的 WSL 才有；没有就用下面三行
# wsl --export Ubuntu-22.04 D:\ubuntu.tar ; wsl --unregister Ubuntu-22.04 ; wsl --import Ubuntu-22.04 D:\WSL\Ubuntu-22.04 D:\ubuntu.tar

2.4 代码放在哪、用什么编辑

  • 源码和构建目录一律放在 WSL 的家目录（~/）里，不要放 /mnt/c、/mnt/d——那是跨系统的文件共享，编译会慢一个数量级。 Windows 资源管理器里输入 \\wsl$\Ubuntu-22.04\home\<你> 能直接看到这些文件。
  • 编辑器：VS Code + WSL 扩展（在 Ubuntu 里 code .），装 clangd 扩展。plugin-build.sh 每次会在 .so 旁边写一份 compile_commands.json， clangd 用它做跳转和补全；LLVM 自己的 cmake-build-release/compile_commands.json 也在。习惯 CLion 的话，CLion 支持 WSL 工具链。
  • 换行符：git config --global core.autocrlf input。脚本要原样带去公司的 Linux，CRLF 会让 bash 报 $'\r': command not found。

§4

从 GitHub 源码编 llvm-project 14.0.0

4.1 为什么还要自己编（apt 版已经能用）

  • 断言打开：cast<>、getAs<> 用错、迭代器失效，在本地当场断言并给出调用栈，而不是到公司的业务代码上才莫名崩溃。公司那份大概率不开断言。
  • 是你要的"基于 GitHub 的 llvm-project"：源码就在手边，CSA 内部（ExprEngine、CallGraph、CFG）可以直接读、加打印、用 gdb 跟。
  • 能预演公司的注册方式（§4.4）：把 checker 编进 clang 本体，验证 Checkers.td 条目、注册函数名、子目录源文件。

4.2 命令

./20-fetch-llvm.sh     # git clone --depth 1 --branch llvmorg-14.0.0 → ~/llvm-project-14，切到本地分支 rb-local，核对 tag 提交 329fda39
./30-build-llvm.sh     # cmake + ninja，产物 ~/llvm-project-14/cmake-build-release（与公司的目录名一致）
LLVM_KIND=src ./40-smoke.sh

GitHub 慢或不通：在浏览器里从 GitHub Releases 下载 llvm-project-14.0.0.src.tar.xz（约 101 MB），然后

LLVM_TARBALL=/mnt/c/Users/<你>/Downloads/llvm-project-14.0.0.src.tar.xz ./20-fetch-llvm.sh

脚本先核对 sha256（35ce9edb…e07e23，沙箱实际下载核对实测数据），再解压成一个 git 仓库并打上 llvmorg-14.0.0 标签，后面的步骤完全一样。

4.3 构建配置（30-build-llvm.sh）

选项 值 为什么
CMAKE_BUILD_TYPE Release 与公司的 cmake-build-release 一致；Debug 版构建目录要大几倍
LLVM_ENABLE_ASSERTIONS ON（ASSERTIONS=OFF 可关） 见 §4.1；要与公司完全一致时关掉，另用一个 LLVM_BUILD 目录
LLVM_ENABLE_PROJECTS clang 只要 clang（含 CSA）
LLVM_TARGETS_TO_BUILD X86 分析只用前端；aarch64 的 TargetInfo 在 clang 前端里，不需要 AArch64 后端
LLVM_USE_LINKER lld 链接 clang 快、省内存
LLVM_CCACHE_BUILD ON 切分支、重配置后少编很多
LLVM_PARALLEL_COMPILE_JOBS / LINK_JOBS 按内存自动算（内存 GB/2、内存 GB/6） WSL 里最常见的失败是编译被 OOM 杀掉
LLVM_ENABLE_PLUGINS ON -load 插件要靠它
编译目标 clang llvm-config FileCheck count not llvm-config 给插件取编译参数；后三个是将来跑 lit 测试用的

实测实测数据：全量约 90 分钟（2 361 个编译步骤），编译时抽查内存占用约 2.5 GB；构建目录 1.0 GB（clang-14 本体 134 MB），ccache 0.14 GB； 产物 clang version 14.0.0 (https://github.com/llvm/llvm-project.git <提交号>)。gcc 13 需要的补丁只有两行（llvm/include/llvm/Support/Signals.h、Base64.h 各加 #include <cstdint>）， 脚本把它作为 rb-local 上的一个单独提交；gcc 13 还会打出几百条 -Wmissing-template-keyword 之类的警告，不影响结果。 8 核按编译并发线性外推约半小时推断。

4.4 可选：在本地预演公司的注册方式

./50-intree-rehearsal.sh          # 默认拿 I0 探针做
./50-intree-rehearsal.sh --undo   # 撤销

它在单独的分支 rb-rehearsal 上用 land.py --into llvm 做三件事：给上游 Checkers.td 补上 rb.enhance.core / rb.enhance.ipa 两个包块并把条目追加进去、 把源文件追加到 clang/lib/StaticAnalyzer/Checkers/CMakeLists.txt、拷贝源码（入口平铺，引擎在 OobSummary/ 子目录）；然后增量编译 clang， 不 -load 直接跑同样的用例，与插件模式和基线比对。沙箱实测实测数据：增量编译 801 秒（2 核；改 Checkers.td 会让全部 checker 重编，共 201 步），-analyzer-checker-help 里出现 rb.enhance.core.OobSummaryProbe， 不 -load 的输出与插件模式、与基线一致；--undo 后重编只用了 43 秒（ccache 命中）。

插件模式验证"代码对不对"，这一步验证"注册对不对"——带去公司之前做一次，往返就少一次。

§5

日常开发循环

代码从哪来：我交付的代码包 oob-summary-v0.N.tar.gz（07- 的 WP0、WP1 起），目录布局镜像 BXPlugin，带 drop.manifest 和 land.py；或者你自己写。 建议在本地建一个 git 仓库 ~/oob-summary：每个版本解压覆盖后提交，你自己的修改也提交在这里——带去公司的就是这个仓库的某个提交，两边对得上。

cd ~/oob-summary
D=~/infer-research-kit/08-summary2-design/devenv
# 编插件（几秒）：入口 + 子目录里的引擎源码
$D/plugin-build.sh build/OobSummary.so OobSummaryChecker.cpp OobSummary/*/*.cpp -I .
# 跑一个用例：checker 名与公司完全一致
$D/cc1-run.sh -load build/OobSummary.so -checker=rb.enhance.ipa.OobSummary \
    ~/infer-research-kit/08-summary2-design/cases/lv1/lv1_01_stat_enum_butt.c
# 近似公司的 4 字节指针 + 大端
TRIPLE=armebv7-linux-gnueabi $D/cc1-run.sh -load build/OobSummary.so -checker=rb.enhance.ipa.OobSummary <文件.c>

（上面的文件名是 WP 代码到了以后的样子；现在可以拿探针把同样的命令走一遍，见 40-smoke.sh 第 3、4 步。）

调试：gdb --args ~/llvm-project-14/cmake-build-release/bin/clang -cc1 -analyze -load build/OobSummary.so …； 有用的开关：-analyzer-checker-help、-analyzer-config-help、-analyzer-display-progress、-analyzer-stats。 插件报 undefined symbol：插件和 clang 不是同一套 LLVM（LLVM_KIND=apt 编的插件只能给 apt 的 clang 用，src 同理），用同一个 LLVM_KIND 重编。

§6

带去公司（每一轮）

  1. 本地打包：只打我们自己的代码，LF 换行，附 sha256。 bash cd ~/oob-summary && git archive --format=tar.gz -o ~/oob-summary-v0.N.tar.gz HEAD && sha256sum ~/oob-summary-v0.N.tar.gz
  2. 按公司的安全规定把这个包传到公司电脑。
  3. 公司电脑上： bash sha256sum oob-summary-v0.N.tar.gz # 与本地的对一下 mkdir -p ~/oob-summary-v0.N && tar xzf oob-summary-v0.N.tar.gz -C ~/oob-summary-v0.N cd ~/oob-summary-v0.N python3 land.py --drop . --into bxplugin --root /usr1/BXPlugin # 先演示：列出要拷的文件和三处登记的 diff python3 land.py --drop . --into bxplugin --root /usr1/BXPlugin --apply # 再落地（重复执行安全，落过的跳过） cd /usr1/BXPlugin/cmake-build-release-release && make -j16 # 然后按代码包 README 里的 bxen 命令跑 TestCase 与业务代码 land.py 做的就是 csa-checker-dev 的五处落点：源码进 xir/llvm_ast/StaticAnalyzer/Checkers/、CMakeLists.txt 的 add_library() 末尾追加、 Checkers.td 对应包块的最后追加、用例目录进 xir/llvm_ast/TestCase/、TestCase/CMakeLists.txt 最后追加 add_subdirectory。 找不到预期结构（比如包块结尾 } // end "rb.enhance.ipa"）就停下来，不猜。撤掉：同样的命令加 --remove --apply。
  4. 带回来：只带不敏感的结论——告警条数、耗时、我们自己用例上的输出、fork-facts.sh 的输出。业务代码与业务告警原文按公司规定处理。

沙箱里在模拟的 BXPlugin 目录上验证过：落地 → 再执行一次（全部跳过）→ 撤掉，git status 回到干净实测数据。

节 回答什么 影响本地的什么
