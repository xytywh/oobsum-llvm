方案按五个问题拆开比，摘要看真实的 JSON

一个完整方案要同时回答五个问题：摘要里存什么、怎么生成、按什么顺序、在哪判定、跨文件怎么跑。旧的 A–G 各自只回答了其中一两个，所以看着不正交。 下面先把选项摆成矩阵、拼成完整方案；再用 16 个用例的 104 份函数摘要 JSON 逐个看多层越界是怎么判出来的——每一步都由回放器在调用点重做代换核对过。 摘要里的自然语言只在 doc 字段里、只给人看；去掉 doc 就是完整摘要，静态分析只读其余字段就能推到最终告警。

A

五个问题与选项

05- §5 列的 A–G 是七个"方案"，但它们回答的不是同一个问题：A 讲生成顺序和在哪判定，B、C 只讲调度方向，D 讲数据结构， E、G 讲判定手段，F 只讲消费方。把它们放在一张表里比，相当于把"用什么发动机"和"装在哪辆车上"并列。

一个完整的方案必须同时回答五个问题：摘要里存什么、怎么生成、按什么顺序生成、在哪里消费和判定、跨文件怎么跑。 每个问题有几个选项，一个方案就是"每个问题各选一个"。下面先把五个问题和选项列清楚（A.1），再把旧的 A–G 放回格子里（A.2）， 最后拼成几个完整方案来比（A.3）。

点一个完整方案，看它在每个问题上选了什么；点"旧 A–G"，看旧编号实际落在哪几格。

Q1摘要里存什么
①只存前置条件 ReqInfer BufferOverrun；V 形、getter、校验函数做不了
②Req + 固定词表的效果 Eff再加新对象及大小、返回值范围、条件效应、字段写
③只存依赖关系谁流到哪个访问，不带数值；适合预筛、切片
④析取 / 路径敏感摘要每条路径一份；分支精度高，但条件数指数增长
Q2摘要怎么生成
①自研抽象解释，跑在 FIR 上不依赖 ExprEngine；全函数性；可单测、可离线
②收割 CSA ExprEngine 结果复用现成；路径爆炸处没有事实
③事实导出 + Datalog 规则规则可读、易增量；数值精度低
④LLM 生成 / 补全覆盖库与业务契约；不可证明，只当候选
Q3按什么顺序生成
①自底向上全部算SCC 逆拓扑序，每函数一次；与层数无关
②按需（从访问点往上追）只算相关的；适合增量；调度复杂
③自顶向下传入口事实最简单；调用点一多就合并失真
Q4在哪消费、在哪判定
①引擎在调用点代换判定本设计；不依赖 ExprEngine；非路径敏感
②CSA 探索时用摘要代替 inlineSummaryApplyChecker 方向；路径精度高；链顶爆炸时走不到
③摘要库上查询判定SQL / Datalog；找候选、做统计
④LLM 读切片 + 摘要研判业务语义；按条计费、不可复现
Q5跨文件怎么跑
①多轮 TU 扫描 + 工作表轮数取决于调用链跨文件次数
②导出 FIR → 离线求解 → 出告警固定两遍；跨 TU 与同 TU 一样
③CSA CTU跨 TU 加载 AST 再 inline；深度问题不变
④全程序值流图要全程序指针分析；重、难增量

推荐、演进与要拍板的事

  • 年内走 S1。 三条决定性的理由：Q2② 会继承路径爆炸（立项要解决的就是它）；Q1① 串不起 V 形与字段 （承诺场景里 LV4-01、LV5-01、LV5-06 都是）；Q5② 的遍数不依赖调用图形态。
  • P1：在 S1 上加 Q4②，即 S3。 对 L2 做一次 CSA 路径确认，降误报、告警带路径；可以在你们现有的 SummaryApplyChecker 上演进， 它要读的就是 Part B 这种 JSON。
  • 2027： Q3②（按需 + 增量，S4）；Q2④ + Q4④（AI 补模型 / 规格、研判账本里的候选）；Q1③（依赖摘要）作大函数预筛。
  • 不选： Q1④（析取摘要，路径爆炸换个地方出现）；Q3③（合并失真）；Q5③（还是 inline）。

B.1

自然语言只给人看，去掉它就是完整摘要

结论：摘要文件里的内容分两类。

  • 键名为 doc 的（出现在任何一层，字符串或对象）：只给人看——用形参名渲染的一句话、源码原文、宏的值、"为什么这样判"。 引擎读入时把所有 doc 整棵删掉，代换、判定、上传、记账、出告警、算指纹都不读它；生产运行默认根本不写（06- I-25 Emit=machine）。
  • 其余全部是机器字段：整数、枚举、规范表达式、对象、位置、函数键。去掉 doc 剩下的就是完整摘要： 静态分析只读这些字段，就能在每个调用点代换、判定，并一路组合出最终告警——位置、英文消息、调用链 note、指纹全部由它们生成。

v3.13 的样例没把这条线划清：可读文本（text、note、detail、msg、实参原文 ptr、对象描述 object）和机器字段混在同一层。 而且有两样东西引擎其实要用、却只写在文本里——访问的是哪个对象（告警里要写 'szName'，指纹要用它）、指针实参指向哪个对象。 v3.14 把这两样改成机器字段 obj（写法见下），其余文字统一挪进 doc；L2 消息里 v3.13 手写的 "in Ue_InitTbl" 机器字段里没有，去掉了（06- D15）。

怎么证明"只读机器字段就够"（cases/summaries/replay.py，全部实测数据）

检查 做法 结果
结构上关死 summary.schema.json 里除 doc 外每个对象都是 additionalProperties: false：多出一个键（比如顺手加的 "note": "…"）校验就不过 104 份全部通过
不许混入自然语言 doc 之外出现中文或成句的英文就报错 0 处
逐调用点核对 ① 计算前先删掉全部 doc；在每个调用点把被调者的 Req / Eff 代进来，结论与 JSON 记的比 16 个用例 0 处不一致
从局部事实推到底 ② 只拿每个函数自己当场算出来的东西——本函数访问点生成的 Req（depth 0）、调用点的实参（值、指针的 obj / have / 字段）、局部区间、守卫——自底向上把上传的 Req、判定、入口账本全部重新推一遍，再按 06- F-30…F-34 组装最终告警 推出上传 Req 58 条、判定 13 条、入口账本 8 条，与 JSON 一致；最终告警 13 条，与 @expect 一致，与 alerts.json 逐条相同
删掉 doc 再跑 --strip DIR 写出 104 份机器版，--dir DIR 从机器版重跑 最终告警文件逐字节相同；回放输出只有实参的显示名不同（没有原文就显示 local:szName）
改坏能抓到 在机器版里改一个 obj、改一个访问点的 end、塞一个 note、往字符串里写中文 分别报出：推出的 Req / 判定与 JSON 不同（指出字段与指纹）、depth-0 访问自相矛盾、schema 不过、doc 之外有自然语言

B.2

调用点上怎么判

  1. 取被调者的摘要（calls[].callee）。
  2. 建代换表：整数形参 p_i ↦ args[i]；ext(p_i) ↦ args[i].have；对象 *p_i ↦ args[i].obj；字段 p_i->f ↦ args[i].fields.f，或经 alias 改写成调用方自己的字段符号。
  3. 代换并化简：end、have、guard 全部代进来，同类项先抵消；locals 里的局部换成区间，同时生成"区间非空"的守卫（循环至少执行一次）。
  4. 判定：
代换后的情况 结论
守卫为假 安全：这次调用走不到访问（LV2-09 TN 传 0）
end 上界 <= have 安全
end 下界 > have L1：所有取值都越界
上界 > have >= 下界，上界来自代码（校验、掩码、循环界、分支常量、返回值范围、守卫） L2
同上，但上界只来自类型范围 / widening 记账，不报（LV10-04 的 UINT16）
还含调用方的接口符号，have 已知，且这些符号都被代码给出的界框住（访问侧校验带上来的守卫、调用点的守卫） 按界判 安全 / L1 / L2（LV3-03、LV4-06）
还含调用方的接口符号，其余情况 上传成调用方的 Req（depth + 1，path 前面加上本调用点）
含调用方局部且没有界 记账
到入口还没判完 记账（entry_unproven；只有类型范围的记 type_range_only）
  1. 应用效果：ret_new / ret_int / ret_cond / field 写进调用方在这个调用点之后的状态（LV4-01 的 new(512)、LV4-06 的条件效应、LV5-01 的 ulUsed）。

报不报：max(depth, eff_depth) > InlineDepth（默认 2）才报，≤ 2 层归现有规则（06- F-20）。16 个用例的判定全部是 3 层，都报。

比 06- 评审稿更细的三处（已同步进 06- v3.13）： * securec 的真实语义文档：memcpy_s 在 destMax == 0 或 destMax > SECUREC_MEM_MAX_LEN（默认 0x7fffffff）时直接返回、不写； count > destMax 时先把 dest 的 destMax 字节清零再返回。所以目的一侧写 destMax 字节，源一侧只有 count <= destMax 时才读（源那条带守卫）， 可能回绕的 destMax（128 − ulOff）生成守卫 ulOff <= 128（LV2-03 TN）。 * 守卫界判定：上表倒数第三行（06- F-12b）。 * 被覆盖的访问只留最强的：同一对象、条件恒更弱的访问并进强的那条，记在 absorbed 里（LV1-02 的 pszName[0]、pszName[1]）（06- A-44）。

B.3
