A

五个问题与选项

05- §5 列的 A–G 是七个"方案"，但它们回答的不是同一个问题：A 讲生成顺序和在哪判定，B、C 只讲调度方向，D 讲数据结构， E、G 讲判定手段，F 只讲消费方。把它们放在一张表里比，相当于把"用什么发动机"和"装在哪辆车上"并列。

一个完整的方案必须同时回答五个问题：摘要里存什么、怎么生成、按什么顺序生成、在哪里消费和判定、跨文件怎么跑。 每个问题有几个选项，一个方案就是"每个问题各选一个"。下面先把五个问题和选项列清楚（A.1），再把旧的 A–G 放回格子里（A.2）， 最后拼成几个完整方案来比（A.3）。

点一个完整方案，看它在每个问题上选了什么；点"旧 A–G"，看旧编号实际落在哪几格。

Q1摘要里存什么
①只存前置条件 ReqInfer BufferOverrun；V 形、getter、校验函数做不了
②Req + 固定词表的效果 Eff再加新对象及大小、返回值范围、条件效应、字段写
③只存依赖关系谁流到哪个访问，不带数值；适合预筛、切片
④析取 / 路径敏感摘要每条路径一份；分支精度高，但条件数指数增长
Q2摘要怎么生成
①自研抽象解释，跑在 FIR 上不依赖 ExprEngine；全函数性；可单测、可离线
②收割 CSA ExprEngine 结果复用现成；路径爆炸处没有事实
③事实导出 + Datalog 规则规则可读、易增量；数值精度低
④LLM 生成 / 补全覆盖库与业务契约；不可证明，只当候选
Q3按什么顺序生成
①自底向上全部算SCC 逆拓扑序，每函数一次；与层数无关
②按需（从访问点往上追）只算相关的；适合增量；调度复杂
③自顶向下传入口事实最简单；调用点一多就合并失真
Q4在哪消费、在哪判定
①引擎在调用点代换判定本设计；不依赖 ExprEngine；非路径敏感
②CSA 探索时用摘要代替 inlineSummaryApplyChecker 方向；路径精度高；链顶爆炸时走不到
③摘要库上查询判定SQL / Datalog；找候选、做统计
④LLM 读切片 + 摘要研判业务语义；按条计费、不可复现
Q5跨文件怎么跑
①多轮 TU 扫描 + 工作表轮数取决于调用链跨文件次数
②导出 FIR → 离线求解 → 出告警固定两遍；跨 TU 与同 TU 一样
③CSA CTU跨 TU 加载 AST 再 inline；深度问题不变
④全程序值流图要全程序指针分析；重、难增量
A.4–A.5

推荐、演进与要拍板的事

  • 年内走 S1。 三条决定性的理由：Q2② 会继承路径爆炸（立项要解决的就是它）；Q1① 串不起 V 形与字段 （承诺场景里 LV4-01、LV5-01、LV5-06 都是）；Q5② 的遍数不依赖调用图形态。
  • P1：在 S1 上加 Q4②，即 S3。 对 L2 做一次 CSA 路径确认，降误报、告警带路径；可以在你们现有的 SummaryApplyChecker 上演进， 它要读的就是 Part B 这种 JSON。
  • 2027： Q3②（按需 + 增量，S4）；Q2④ + Q4④（AI 补模型 / 规格、研判账本里的候选）；Q1③（依赖摘要）作大函数预筛。
  • 不选： Q1④（析取摘要，路径爆炸换个地方出现）；Q3③（合并失真）；Q5③（还是 inline）。

讨论时值得请专家拍板的几件事

  1. Q4：L2 要不要先经 CSA 二次确认再报？（即 S3 是否提前到年内。）取决于你们对 L2 误报的容忍度。
  2. Q1 的效果词表：字段只跟踪"经形参两次解引用以内"，全局变量的值年内不跟踪（只用全局数组的大小），是否够用？
  3. 判定口径（B.2）：L2 只认代码给出的上界，类型范围不报；入口函数的形参被访问侧的校验框住时直接判 L2（LV3-03、LV4-06）是否接受？
  4. Q5②：一遍导出全量 FIR 的磁盘占用与求解内存（探针 R3 会给出全量的函数数与规模）。
  5. 账本（opens）作为 AI + 程序分析的输入：Lv7–Lv10 的漏报都会在这里留下带原因的记录（B.1 的格式）。
B.1

一份摘要文件长什么样

一个函数一份 JSON。 全量运行时落在 WorkDir/summaries/<00..ff>.jsonl（每行一份），oobsum.py show <函数名> 把一份打印成下面的样子； 本包的 104 份样例在 cases/summaries/<用例>/<函数名>.json，格式定义在 cases/summaries/summary.schema.json（JSON Schema，104 份全部校验通过）。

顶层字段

字段 含义 例
fn、key、loc 函数名、跨 TU 唯一的键（06- D-01…D-08）、定义位置 "F:Ue_InitTbl"
params 形参 "名字: 类型"；表达式里的 p0、p1… 按下标对应它们 ["pstTbl: UE_S*", "ulNum: UINT32"]
fields 摘要用到的字段符号：偏移、大小、类型（按目标 ABI） "p0->ulBufLen": {"off": 4, "size": 4}
status analyzed / partial:原因 / skipped:原因——"没分析"和"分析了没问题"分得开
reqs 前置条件：调用方必须满足、否则本函数（或它调用的函数）里会越界 见下
effs 效果：对调用方有用的输出（新对象及大小、返回值范围、条件效应、写了哪个字段） {"kind": "ret_new", "size": "p0"}
calls 调用点记录：本函数的每个结论是从哪个调用点、哪次代换来的——调试与追溯就看它 见下
reps 在本函数判定的越界（汇合点在这里） {"level": "L2", "depth": 3, ...}
opens 账本：判不了的地方和原因（漏报都在这里留痕） {"reason": "pointer_stepping", ...}

一条 Req（以 Ue_InitTbl 为例：ulIdx 在循环里被换成了 [0, ulNum − 1]；// 后面是这里加的说明，文件里没有）

{
  "id": "R1", "kind": "W", "bytes": "4", "obj": "*pstTbl",
  "have": "ext(p0)",                         // 从 pstTbl 起对象还剩多少字节
  "end": ["4", "16*p1 - 12"],                // 访问末端（偏移 + 字节数）的 [下界, 上界]
  "start": "0", "bound": "loop",             // 上界来自循环界——只有代码给出的上界才能判 L2
  "guard": ["p1 >= 1"],                      // 循环至少执行一次才有这次访问
  "access": {"fn": "Ue_InitOne", "at": "lv4_01_wrapper_alloc_spec.c:52", "code": "pstTbl[ulIdx].ulState = 0"},
  "path": ["Ue_InitTbl@lv4_01_wrapper_alloc_spec.c:59", "Ue_InitOne@lv4_01_wrapper_alloc_spec.c:52"],
  "depth": 1, "eff_depth": 0, "blind": false,
  "text": "ulNum >= 1 ⇒ W4 @ *pstTbl，末端 [4, 16*ulNum - 12]；需 16*ulNum - 12 <= ext(pstTbl)"
}

安全条件统一读作 end 的上界 <= have；text 是用形参名渲染的可读形式（派生字段，读入时忽略）。

表达式写法（都是字符串，人能直接读，C++ 侧用一个小解析器读）

写法 含义
16*p1 - 12 形参的线性式（整数系数）
ext(p0)、ext(p0->pucBuf) 指针还剩多少字节（形参、形参的字段）
p0->ulBufLen 字段在函数入口时的值（具体偏移见 fields）
g:g_x 全局在入口时的值
div(p1, 32)、mod(e, n)、wrap32(p1 - 1)、mul(a, b) 不透明项：除以常数、取模、无符号回绕、两个变量相乘——代换成常数后才求值
p1 <= 31、div(p1 + 31, 32) >= 1 守卫 / 条件

效果的种类：ret_new（返回新对象，size、maybe_null、eff_depth）、ret_ptr、ret_int（返回值范围）、ret_cond（ret == c ⇒ …，校验函数）、 out_new / out_int（出参）、field（写了形参指向的结构体的哪个字段）、global、invalidate。

调用点记录（calls[]）：site、callee、args（整数实参写表达式；指针实参写 {"ptr": 原文, "have": 还剩多少字节, "alias"?: 就是调用方的哪个形参, "fields"?: 栈帧里记着的字段值}）、 locals（实参里用到的本函数局部在调用点的区间）、guards（调用点处成立的守卫，比如条件效应收窄出来的）、results（被调者每条 Req / Eff 在这里的结局： up 上传成本函数的哪条、safe、L1 / L2 对应哪条判定、open 记账原因）。这一节是调试的主要入口：任何一条告警或漏报，都能顺着 calls 一层层找到是哪一次代换得出的。

判定（reps[]）：level、reported（是否真的报——层数过滤后）、site（告警位置：汇合点的调用表达式）、access、object、have、end、bound、 depth / eff_depth、chain（逐层 trace）、msg（英文告警文本）、fp（指纹）。

账本（opens[]）：reason（06- D-27 的枚举）、at、detail；入口处到此为止的 Req 带 req 指回去。

B.2

调用点上怎么判

  1. 取被调者的摘要（calls[].callee）。
  2. 建代换表：整数形参 p_i ↦ args[i]；ext(p_i) ↦ args[i].have；字段 p_i->f ↦ args[i].fields.f，或经 alias 改写成调用方自己的字段符号。
  3. 代换并化简：end、have、guard 全部代进来，同类项先抵消；locals 里的局部换成区间，同时生成"区间非空"的守卫（循环至少执行一次）。
  4. 判定：
代换后的情况 结论
守卫为假 安全：这次调用走不到访问（LV2-09 TN 传 0）
end 上界 <= have 安全
end 下界 > have L1：所有取值都越界
上界 > have >= 下界，上界来自代码（校验、掩码、循环界、分支常量、返回值范围、守卫） L2
同上，但上界只来自类型范围 / widening 记账，不报（LV10-04 的 UINT16）
还含调用方的接口符号，have 已知，且这些符号都被代码给出的界框住（访问侧校验带上来的守卫、调用点的守卫） 按界判 安全 / L1 / L2（LV3-03、LV4-06）
还含调用方的接口符号，其余情况 上传成调用方的 Req（depth + 1，path 前面加上本调用点）
含调用方局部且没有界 记账
到入口还没判完 记账（entry_unproven；只有类型范围的记 type_range_only）
  1. 应用效果：ret_new / ret_int / ret_cond / field 写进调用方在这个调用点之后的状态（LV4-01 的 new(512)、LV4-06 的条件效应、LV5-01 的 ulUsed）。

报不报：max(depth, eff_depth) > InlineDepth（默认 2）才报，≤ 2 层归现有规则（06- F-20）。16 个用例的判定全部是 3 层，都报。

比 06- 评审稿更细的三处（已同步进 06- v3.13）： * securec 的真实语义文档：memcpy_s 在 destMax == 0 或 destMax > SECUREC_MEM_MAX_LEN（默认 0x7fffffff）时直接返回、不写； count > destMax 时先把 dest 的 destMax 字节清零再返回。所以目的一侧写 destMax 字节，源一侧只有 count <= destMax 时才读（源那条带守卫）， 可能回绕的 destMax（128 − ulOff）生成守卫 ulOff <= 128（LV2-03 TN）。 * 守卫界判定：上表倒数第三行（06- F-12b）。 * 被覆盖的访问只留最强的：同一对象、条件恒更弱的访问并进强的那条，记在 absorbed 里（LV1-02 的 pszName[0]、pszName[1]）（06- A-44）。
