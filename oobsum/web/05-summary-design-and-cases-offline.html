多层越界的函数摘要：长什么样、留什么、怎么串，以及 67 个分级用例

摘要回答一个固定的问题："调用方给我什么样的输入，我和我调用的函数里的访问才安全；我给调用方留下了哪些和内存有关的事实。" 相关性由这个问题机械地决定，不靠逐个变量判断。条件在调用点代换后逐层上传，到汇合点判定；判不了的记账，绝不当成安全。

§0

先回答你问的几件事

  1. 摘要到底留什么、扔什么？ 不是逐个变量"挑"出来的。摘要回答一个固定的问题： "调用方给我什么样的输入，我（连同我调用的函数）里的内存访问才安全；我给调用方留下了哪些和内存有关的事实。" 一个量出现在摘要里，当且仅当它经数据依赖、或经支配访问的校验，流进了某个访问的基址、偏移、长度，或者流进了某个对外效果。 日志调用不出现，不是因为有一条"删日志"的规则，而是它什么都没流进去（§1.2 有一个 20 行函数只剩 2 条条件的例子）。
  2. 摘要生成是不是可判定的？ 精确的摘要不可判定（Rice 定理）；我们算的是近似，计算一定终止（widening、迭代上限、全函数性）。 所以问题不在"算不算得出"，在"算出来的有多准"。处理办法是三值：证明安全 / 证明越界（L1、L2）/ 判不了。 判不了就往上传，到入口还判不了就记账，绝不当成"安全"——每一条丢失都有原因可查（§1.3）。
  3. 能结合切片吗？ 能，而且摘要本质上就是"访问点的后向切片，投影到函数接口上，再用抽象域压缩"。 有三种结合方式：隐式切片、先算依赖摘要的两段式、显式跨函数切片给 AI（§1.4）。
  4. 摘要一定是单函数的吗？ 默认单函数，但不是唯一选择：递归按强连通分量算，薄转发函数可以折叠， 必要时按调用上下文分开，模块边界只导出接口摘要（§1.5）。
  5. 不跨函数能拿到什么、要跨多少层？ 局部数组加常量、成员类型给出的大小、函数自己校验过的访问，都不跨函数就定了—— 真实代码里多数函数的条件集是空的。跨多少层不预设：条件一直往上走，直到被判定、变得无用、或到达入口（§1.5）。
  6. 风险在哪？ 不在终止性，也不在规模（每个函数只分析一次）。在三处：别名和未知调用导致效果漏算、条件数量膨胀、 抽象域表达不了的关系。每一处都有账可查（§1.6）。
  7. 怎么串联起来完成检测？ 调用点上做五步代换（§3），每一级的组合方式在 §4，67 个用例逐个写了。
  8. 多个摘要读写检测的备选方案：七种（§5）。推荐 A（自底向上条件 + 效应）做主干，C（按需查询）做调度优化， F（CSA 消费摘要）做告警确认与路径解释，E（事实查询）和 G（切片 + LLM）对接 AI。
  9. 用例：Lv1–Lv10 共 67 个（134 个入口），全部能编译；用 Infer 当标尺跑过：134 个入口里 104 个与期望一致， 年内要报的 41 个（32 个承诺 + 9 个尽力）里 Infer 报出 13 个、级别全对，漏掉的 28 个正好落在安全函数、全局表、校验界、字段这几类（§6）。
§1

根本问题

1.1 摘要回答的是什么问题

对函数 f，它的接口是：形参、读到的全局、经形参能到达的结构体字段（深度有限）、返回值、出参。 摘要是四样东西：

部分 内容 例子
Req 前置条件 一组关于接口的条件；调用方都满足时，f 和它调用的函数里的访问都不越界 需 8·ulNum ≤ ext(pstItem)
Eff 效果 和内存安全有关的输出：新对象及其大小、返回值 / 出参 / 被写字段 / 被写全局的取值或关系、条件效果 ret = new(ulSize)、ret ∈ [0, 8]、ret ≠ 0 ⇒ ulId ≤ 16
Rep 已判定 在 f 内部已经能判定的越界（不依赖接口），带 trace L1：需 17 ≤ ext(szName)=16
Open 账本 没算进来的东西和原因 函数指针@Cap_Dispatch、未知函数 Drv_ReadReg、widening 丢关系

关心的：能成为访问的基址、偏移、长度、对象大小的量，以及约束它们的校验和返回值。 不关心的：缓冲区里装的数据（读出来只当一个无约束的符号）、不支配访问的控制流、和上面这些没有数据关系的一切。

"相关"有两个方向，难度不一样：

  • 往回看（Req）：哪些输入会影响我的访问——从访问点往回追，是个明确的问题。
  • 往前看（Eff）：我的哪些输出会影响别人的访问——自底向上算的时候不知道调用方要什么。两种做法： 固定词表（总是算：返回 / 出参指针指向的新对象及大小、整数返回值 / 出参 / 被写字段 / 被写全局的范围）； 按需（调用方有一条未决条件引用到某个输出时，才回头算那一项，结果缓存）。年内用固定词表，按需留作优化（§5 方案 C）。

1.2 "整个函数好像都相关"——相关性是算出来的

cases/demo/relevance_demo.c：

UINT32 Ue_ProcRrcMsg(UE_CTX_S *pstUe, const UINT8 *pucMsg, UINT32 ulMsgLen)
{
    UINT32 ulIeLen;

    LOG_Print(3, "ue %u rrc len %u", pstUe->ulUeId, ulMsgLen);  /* 不进：什么都不流进访问 */
    pstUe->ulRxCnt++;                                            /* 进效应：整数字段写（固定词表） */
    if (pstUe->ulState != UE_STATE_CONNECTED) {                  /* 不进：守卫里没有被跟踪的量 */
        return VOS_ERR;
    }
    if (Timer_Restart(pstUe->ulTimerId) != VOS_OK) {             /* 不进：被调摘要没有条件 */
        Stat_Inc(STAT_TIMER_ERR);                                /* 不进：常量 2 代入"需 ≤ 3"，当场判安全 */
    }
    ulIeLen = pucMsg[1];                                         /* 进：读 pucMsg[1] → 需 2 ≤ ext(pucMsg) */
    if (ulIeLen + 2 > ulMsgLen) {                                /* 进：守卫，约束了 ulIeLen 与 ulMsgLen 的关系 */
        return VOS_ERR;
    }
    (void)memcpy_s(pstUe->aucLastIe, sizeof(pstUe->aucLastIe),   /* 目的：成员 32 字节、destMax 32 → 当场安全，不进 */
                   pucMsg + 2, ulIeLen);                         /* 源：末端 2 + ulIeLen ≤ ulMsgLen → 需 ulMsgLen ≤ ext(pucMsg) */
    return VOS_OK;
}

它的摘要：

Ue_ProcRrcMsg(pstUe, pucMsg, ulMsgLen)
  req R1  R1 @ pucMsg + 1                           需 2 ≤ ext(pucMsg)
  req R2  R ulIeLen @ pucMsg + 2，末端 ≤ ulMsgLen     需 ulMsgLen ≤ ext(pucMsg)
          （ulIeLen 是消息内容，无约束；守卫 ulIeLen + 2 ≤ ulMsgLen 把它"消掉"了）
  eff     pstUe->ulRxCnt := pstUe->ulRxCnt + 1

20 行代码剩下 2 条条件和 1 条效果。决定去留的不是"这个变量重不重要"的判断，而是三件机械的事：

  1. 数据依赖由抽象解释自动追：没有流进访问的量，从来就没进过条件。
  2. 控制依赖只保留支配访问、且提到被跟踪量的条件，作为守卫（ulIeLen + 2 > ulMsgLen）； 其余分支照常合并（ulState 那个判断）——这会丢掉一些相关性，但只会让结论变成"判不了"，不会变成错的。
  3. 被调函数按它们自己的摘要代入：Stat_Inc 的条件当场被常量满足，Timer_Restart 本来就没有条件。

你担心的"任何变量都可能影响访问"是对的，但它只通过三条通道：数据、控制、内存（别名）。 前两条上面已经处理了；第三条——经另一个指针改了我们跟踪的字段——才是真正的风险，见 §1.6。

1.3 可判定性，以及"拿不准怎么办"

  • 精确摘要不可判定：要精确知道"什么输入会越界"等价于判定程序性质，Rice 定理说不行。
  • 近似摘要总能算出来：抽象解释在循环头上 widening、有迭代上限、任何构造都有兜底（降成未知），所以一定终止，一定产出合法摘要 （01- §3.4 的全函数性）。
  • 所以真正的问题是精度，处理原则：
情况 结论 去向
代入后条件对所有取值成立 安全 丢弃
代入后对所有取值都不成立 L1 报
取值范围的上界来自代码（校验、掩码、分支常量、循环界、返回值范围），且部分取值不成立 L2 报
还含有上层的符号 StillOpen 往上传
到入口还含符号 / 上界只来自类型范围 / 上界是 widening 出来的 ∞ / 含非线性项 判不了 不报，记账（带原因）

最后一行很关键：类型范围（UINT16 的 65535）和 widening 的 ∞ 都不算"代码给出的界"，否则每个消息长度字段、每个指针步进循环都会变成告警 （LV7-04、LV8-02 的 TN 就是专门守这一条的用例）。记账就是漏报账本：W10 上真实代码后按原因统计，风险是看得见的。

1.4 摘要能结合切片吗

能。摘要 = 访问点的后向切片 → 投影到接口 → 用抽象域压缩。三种结合方式：

方式 做法 用在哪
隐式切片（现设计） 抽象解释只跟踪"可能流进访问或效果"的量，不单独做切片 摘要引擎本身（年内）
两段式：先依赖、后数值 第一段算依赖摘要：哪些入参 / 全局可能影响哪些访问 / 输出（图可达性，便宜、近似完备）；第二段只在这个切片上算数值摘要 预筛（"这个函数和越界有没有关系"）、大函数瘦身、2027 增量分析的失效依据
显式跨函数切片（SDG，Horwitz–Reps–Binkley） 系统依赖图里的 summary edge 本身就是"依赖摘要"；从访问点切出跨函数的切片 给 AI：Lv8–Lv10 把切片和未证明的条件一起交给 LLM 判

推荐：引擎用隐式切片；第一段依赖摘要作为可选预筛（P1，大函数多时提前）；显式切片作为 AI 接口（2027）。

1.5 摘要的单位，以及要跨多少层

单位的备选：

单位 什么时候用 代价
单函数（默认） 一切正常情况；符号代换让一份摘要适用于所有调用点（"上下文多态"） ——
强连通分量 递归（LV9-05）：分量内迭代到不动点 实现量中等，2027H1
折叠薄转发 只做一次转发的函数（L1 → L2 → L3 那种）可以不单独存摘要，直接拼接 省存储；trace 里仍保留这一层
按上下文分开 同一个函数在不同调用点的行为差别大、符号代换表达不了（比如按标志位走完全不同的分支） 摘要数量膨胀，只对少数函数开
模块边界 模块内部一起分析，只对外导出接口摘要 适合库型模块；与 2027 的增量分析一起考虑

不跨函数就能定的：局部 / 静态 / 定义可见的全局数组配常量下标；成员类型给出的大小（p->aucKey）； 函数自己校验过的访问；安全函数的 destMax 等于目的成员大小。这些在函数内就判定了（安全或越界），不产生 Req。 这是常态：大多数函数的 Req 是空的，只有"信任调用方"的函数才导出条件。

跨多少层：不预设上限。条件一直往上走，直到：被判定（安全 / L1 / L2）；变成无用（含非线性项、类型范围、widening ∞）；或到入口（记账）。 层数只影响 trace 的长度，不影响计算量。工程上的限制在别处：每个函数的条件数（合并同基址同形状的条件，超过上限按严重度保留，其余记账）。

1.6 风险在哪、不在哪

风险 表现 怎么看得见 怎么控
别名导致效果漏算 经另一个指针改了我们跟踪的字段，摘要不知道 → 可能漏报，极少数误报 记"按类型失效"的次数 写 T* 时失效所有被跟踪的、类型为 T 的字段（按类型的保守规则）；真别名不在本期
未知函数的默认假设 乐观（假设不改被跟踪的内存）可能漏报；悲观（全部失效）会让很多条件判不了 记账"未知函数"及其调用次数 已知纯函数（日志、格式化）乐观；其余按参数类型失效；常用的进模型表
条件膨胀 一个函数的条件越传越多 每函数条件数、截断次数 同基址同形状合并（只留最强）；上限截断，按严重度保留
域表达不了的关系 非线性、跨循环、字段不变式 记账原因分类 判不了就不报；按账本决定补什么（2027 / AI）
跨文件不一致 依赖的摘要已过期 指纹不一致 多轮扫描 + 指纹（01- §3.11）

不是风险的：终止性（一定终止）、规模（每函数一次，层间相加；Infer 实测 200 层 0.76 秒）、确定性（同输入同输出）。

摘要的形式

2.1 记法（用例文件头里用的就是这套）

记法 含义
ext(p) 从指针 p 往后还能访问的字节数（对象大小 − p 的偏移）。偏移下传时 ext(p + k) = ext(p) − k
W n @ p + off / R n @ p + off 在 p + off 处写 / 读 n 字节。off 可以是常数、线性式、区间 [a, b]
需 X ≤ ext(p) 这条访问安全的条件（末端不超过对象）
守卫 ⇒ … 只在守卫成立时才有这次访问，例如 ulPortId < 32 ⇒ 需 24·ulPortId + 4 ≤ ext(astPort)
p->f、g_x 字段、全局在函数入口时的值（作符号）
ret = new(E) 返回一个新申请的对象，大小 E；*pp = new(E) 是出参；p->f := E 是字段写
ret ∈ [a, b]、ret ≠ 0 ⇒ x ≤ 16 返回值范围；条件效果（校验函数）
⟨a·b⟩ 保留下来的不透明项（两个变量相乘等），代入后变成常数才参与判定
(x − 1)ᵘ 无符号减法，可能回绕
path A → B → C 条件从访问点上传经过的函数（报告时就是 trace）

§3

怎么把摘要串起来

3.1 调用点上的五步

调用者 c 在调用点 g(a0, a1, …)：

  1. 取摘要：同 TU 的被调者没算过就先算（按需递归）；跨 TU 的查 SummaryDB，没有就记 pending，下一轮再来。 函数指针先解析目标集合（年内只解析同函数内的常量赋值，S9.1），解析不了记账。
  2. 建代换表：param#i ↦ 实参在调用点的抽象值。指针实参是"基址 + 偏移"（aucBuf + 8、new@site、c 的形参）； 整数实参是"线性式 + 区间"；字段路径 param#0->f 映射到实参指向的对象在 c 里记录的字段值。
  3. 代换并化简：把每条 Req 的 ext(param#i) 换成 ext(实参基址) − 实参偏移，把整数形参换成实参表达式； 同类项先抵消（LV3-07 的 ulOff），守卫一并代换。
  4. 用调用点的状态判定：调用点处变量的区间（来自 c 自己的校验、循环、常量）代入，按 §1.3 的表分成 安全 / L1 / L2 / 上传 / 记账。上传的条件改写成 c 的接口符号，path 前面加上 c。

#include "../common.h"

#define MAX_NBR_NUM 16

typedef struct {
    UINT16 usPci;
    UINT16 usEarfcn;
} NBR_S;

typedef struct {
    UINT32 ulNum;
    NBR_S  astNbr[MAX_NBR_NUM];
} NBR_LIST_S;

static void NbrList_Decode(NBR_LIST_S *pstList, const UINT8 *pucMsg)
{
    pstList->ulNum = pucMsg[0];
}

static void NbrList_Decode_OK(NBR_LIST_S *pstList, const UINT8 *pucMsg)
{
    UINT32 ulNum = pucMsg[0];
    pstList->ulNum = (ulNum > MAX_NBR_NUM) ? MAX_NBR_NUM : ulNum;
}

static UINT32 Nbr_Use(const NBR_LIST_S *pstList, UINT32 ulNum)
{
    UINT32 i, ulSum = 0;
    for (i = 0; i < ulNum; i++) {
        ulSum += pstList->astNbr[i].usPci;                   /* ★1 */
    }
    return ulSum;
}

static UINT32 Nbr_Apply(const NBR_LIST_S *pstList)     { return Nbr_Use(pstList, pstList->ulNum); }
static UINT32 Cell_ApplyNbr(const NBR_LIST_S *pstList) { return Nbr_Apply(pstList); }

UINT32 Cell_OnNbrMsg_TP(const UINT8 *pucMsg)
{
    NBR_LIST_S stList;
    NbrList_Decode(&stList, pucMsg);
    return Cell_ApplyNbr(&stList);
}

UINT32 Cell_OnNbrMsg_TN(const UINT8 *pucMsg)
{
    NBR_LIST_S stList;
    NbrList_Decode_OK(&stList, pucMsg);
    return Cell_ApplyNbr(&stList);
}

  • C 是 A 的调度优化：规模吃紧时（W03 的全量空跑耗时会给出答案）提前，否则 2027 与增量一起做。
