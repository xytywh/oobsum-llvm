为什么是这条路

已立项 · D0 / D1

inline 每深一层，路径数成倍增长；摘要让层与层之间变成相加——每个函数只分析一次， Infer 实测 200 层链 0.76 秒，MiniOob 20 层 0.31 秒 实测数据。 引擎不走 ExprEngine，才不会在 CSA 放弃探索的地方跟着缺席：立项输入的根因“路径爆炸”，说的正是 CSA 在那儿没有事实可采。

层数不限制成本，限制精度的是链上每一层做了什么：线性传递无损；分支合并、循环会让区间变宽（L1 可能降为 L2）； 调用没有摘要也没有模型的函数、函数指针、递归会让条件断链；链顶不在分析范围内则一路 StillOpen 不报。

申请函数怎么接

P0-5 · 复用现有输入

两份现成的输入只说了“哪个位置是申请到的内存”，没说“哪个参数是长度”。 解法是不逐个识别封装函数的长度参数，只给最底层分配器补一个字节数下标，其余由摘要分析函数体时自底向上推出—— 多层封装逐层推上去，本身就是“多层”问题。

config.ini · 开发配置

MEM_ALLOC=VOS_MemAlloc,-1
MEM_FREE=VOS_MemFree,1
; 形参从 0 编号，-1 = 返回值
; v3.7 新增（只给底层几个）
MEM_ALLOC_SIZE=VOS_MemAlloc,2 ; 下标待确认
MEM_ALLOC_SIZE=malloc,0
MEM_ALLOC_SIZE=calloc,0*1
+

alloc_free_identity · 识别结果 JSON

func_name   VISPADP_IFMNG_Malloc
func_type   alloc   para -1
inner_wrapped_func  VOS_MemAlloc
offset      []  ← 非空 = 挂在结构体成员上
reason      调用栈（每层带 para / offset）

SummaryGen 分析封装函数体 → ReturnEffect

void *VISPADP_IFMNG_Malloc(UINT32 ulLen) { return VOS_MemAlloc(PID, 0, ulLen); }
    → fresh heap，extent = param#0 字节
void *XX_AllocWithHdr(UINT32 n) { char *p = VOS_MemAlloc(PID, 0, n + sizeof(HDR)); return p + sizeof(HDR); }
    → fresh heap，extent = param#0 + sizeof(HDR)，返回指针偏移 sizeof(HDR)
      （带头部的内存池写法：靠参数名猜长度在这里必错）
情形处理
封装函数的函数体在分析范围内以摘要推导为准；JSON 结果用来交叉校验，不一致记校验日志
函数体不在范围内，但在配置或 JSON 里当作申请函数，extent 记为符号未知：知道是堆、不知道多大，不会误报
同上，且想要大小P1：形参名启发 / 大模型识别，结果标来源，人工确认后才参与 L1
JSON 的 offset按被分析代码同一目标 ABI 换成字段路径；ILP32 与 LP64 的成员偏移不同，建议识别结果同时带字段名路径
释放信息、申请 / 释放配对越界分析用不到，留给以后的 UAF / 泄漏类规则（P2）
