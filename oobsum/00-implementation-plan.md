## 1. 一句话方案

**在现有 CSA 规则之外新建一条"摘要通道"：一个不走 ExprEngine 的抽象解释引擎，给每个函数算出
"越界安全条件"摘要，在调用点把形参代换成实参、逐层往上传，传到数组大小和下标都已知的那一层再判定。
专门补现有规则因路径爆炸而漏掉的 ≥ 3 层调用越界；1–2 层仍由现有规则负责。**

为什么是这条路，一句话：inline 每深一层路径数成倍增长，摘要让层与层之间变成相加
（Infer 实测 200 层 0.76 秒【实测数据】）；而引擎不走 ExprEngine，才不会在 CSA 放弃探索的地方跟着缺席
（`01-architecture.md` §1）。

## 3. 方案全貌

```
                         ┌──────────── 每一轮（bxen 全量模式，按 TU 并行）─────────────┐
compile_commands.json ──▶│  rb.enhance.ipa.OobSummary（check::ASTCodeBody，只建 CFG）   │
（第 1 轮全量，           │    ├─ ExtentModel   数组多大（局部/全局/字段/堆，§3.1）      │
 第 2 轮起只跑工作表）    │    ├─ AccessPath    基址怎么表示（形参/全局/字段/偏移，§3.2）│
                         │    ├─ SummaryGen    算摘要：区间 + 阈值 widening（§3.4）       │
                         │    ├─ Applier       调用点代换 → L1/L2/StillOpen（§3.6）      │
                         │    └─ 同 TU 被调者按需递归；跨 TU 被调者查库，没有就 Pending   │
                         └───────────────┬──────────────────────────────┬──────────────┘
                                         ▼                              │
            SummaryDB（SQLite）：summaries / globals / reports / deps   │
                                         │                              │
      驱动脚本：从库里算出"被调者已就绪的 Pending 函数所在 TU" ─────────┘  → 下一轮
                                         │ 工作表清空（或到轮数上限）
                                         ▼
                   导出告警（bxen 现有格式 + 指纹 + 逐层 trace）
```

输入还有两份现成的：**`config.ini` 的 `MEM_ALLOC` / `MEM_FREE`** 与 **`alloc_free_identity` 的识别结果 JSON**。
封装分配器"申请多大"不逐个去识别，只给最底层分配器（`VOS_MemAlloc` 等）补一个字节数下标，
其余由摘要自底向上推出来（`01-` §3.7）。

## 11. 风险（前五条）

| 风险 | 应对 |
|---|---|
| 链上调了没摘要也没模型的函数，条件断掉（层数越多越容易遇到） | 模型表 W08 起步；每个函数的摘要记断链原因，W10 按统计补模型 |
| 人力只有一个人，P0 上沿超出期限 | W04 起补 0.5 人；§6 的砍项顺序 |
| 多轮扫描耗时超预期 | W03 先量空跑耗时；超了就按子系统分批，或把方案 B 的 IR 导出部分提前 |
| 真实代码误报高于语料 | W10 就上真实代码，不等到最后；先只出 L1 |
| ILP32 布局：上游 clang 14 把目标按 LP64 算，`alloc_free_identity` 的 `offset` 也可能按另一种 ABI 算 | G0 前确认 fork 的 ABI（T0-1c）与 `offset` 的来源；识别结果带上字段名路径 |
