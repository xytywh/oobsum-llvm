# SPEC-0020 F-03 destMax 回绕的第二区间；模型给出的守卫总挂在这次访问上

状态：已实现
来源：用户决定（2026-10-16，STATUS"等用户提供"里 SPEC-0018 §3 的问题："按你的决定来"——补）；06- F-03、SPEC-0018 §2.2、SPEC-0016 §2.2（守卫挑选）。

## 1. 要解决什么

securec 只在 `0 < destMax <= 0x7fffffff`（`SECUREC_MEM_MAX_LEN`）时写。`destMax = wrap32(E)`（`128 − ulOff`）时，F-03 原文只看 `E >= 0` 这一段（守卫 `ulOff <= 128`、`destMax = E`），
但 `E <= 0x7fffffff − 2^32`（`ulOff >= 2^31 + 129`）时 `wrap32(E) = E + 2^32 ∈ [129, 2^31 − 1]`，securec **照样写**——这一段的越界会漏。

## 2. 设计

### 2.1 两段

`destMax` 的值是 `wrapW(E)`（单个回绕项）时，这次调用的访问按两段各生成一遍：

| 段 | 守卫 | `destMax` 取 |
|---|---|---|
| A | `E >= 0` | `E` |
| B | `E <= −1` 且 `E <= 0x7fffffff − 2^W`（W = 32 时就是 `E <= −2^31 − 1`） | `E + 2^W` |

某一段的守卫在类型范围与已有守卫下不可能成立（能证明 `E >= 0x7fffffff − 2^W + 1`，或常数为假）→ 那一段不生成。`E` 的取值都在 `[0x7fffffff − 2^W + 1, −1]` 里的
（回绕后大于上限）两段都不在，securec 不写。

### 2.2 模型给出的守卫总挂上

SPEC-0016 只挂"与 Req 的 have / end / start 有公共符号"的守卫。模型给出的守卫（段守卫、`when`）是这次访问**发生的条件**，总挂在这次访问的 Req 上——
除非被同一条 Req 上的其余守卫蕴含（`EntailsLe0`）。第一段的源 `p1 + p3 <= 128` 蕴含 `p1 <= 128`，所以金标准里第一段的写法不变；
第二段的源是 `p1 + p3 <= 4294967424` 且 `p1 >= 2147483777`，缺了后者就会把"第一段里 `count > destMax`、不读源"的情形也算成读。

### 2.3 金标准

LV2-03 `Tlv_WriteVal_OK` 多两条局部 Req（第二段的目的 `end 4294967424`、守卫 `p1 >= 2147483777`；第二段的源），上层（`Tlv_Append_OK`、`Pkt_AddIe_OK`）各多两条上传，
在 `Pkt_Build_TN`（`ulOff = 16`）处守卫为假、判安全。用 `golden_regen.py` 重算。告警不变。

## 3. 对召回与误报的影响

补上偏移超过 2 GB 时的漏报；第二段的守卫只在实参可能那么大时才不为假，正常调用点上判安全，不增加误报。
