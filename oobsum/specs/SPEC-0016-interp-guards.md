# SPEC-0016 函数内解释第二步：条件边与守卫（06- A-14、A-30）

状态：已实现（S7b）
来源：`STATUS.md` S7b；06- §6.2 A-14（守卫：至多 8 个只含接口符号的原子 `LE ≤ 0`，先进先出；来源是 `assume` 边）、A-15（合并时守卫取交集）、
§6.3 A-30（`assume`：收窄局部；两边常数且为假 → 边不可达；含接口符号 → 加守卫）、A-44（守卫不同的 Req 不合并）、D-25（调用点的 `guards`）；
金标准 `LV2-09/Hist_GetPrevSafe`（`if (ulPos == 0) return; … aucHist[ulPos - 1]` → `end [p1, p1]`、`guard ["p1 >= 1"]`）。

## 1. 要解决什么

S7a 不看条件边，`if (ulPos == 0) return;` 之后的 `aucHist[ulPos − 1]` 仍按回绕算成 `wrap32(p1 − 1) + 1`，于是 LV2-09 的 TN（实参 0）被误报 L1。
条件边要变成守卫：访问只在守卫成立时发生；守卫也让"无符号减法不会为负"能被证明。

## 2. 设计

### 2.1 条件 → 原子

`assume` 的条件是比较（`cmp`）、`!x`，或它们的按位与（`switch` 的 `default`，SPEC-0009 §2.2）。比较两边先求值：

* 两边都是确切值：`a < b` → `a − b + 1 ≤ 0`；`a <= b` → `a − b ≤ 0`；`>`、`>=` 对称；`a == b` → 两个原子；`a != b`：若一边是常数 `c`、另一边 `x` 的下界
  （形参类型范围与已有守卫，`core/Range` 的 `SymEnv`）正好是 `c` → `x ≥ c + 1`，上界正好是 `c` → `x ≤ c − 1`，否则不产生原子（`!=` 本身不是线性约束）。
* `!x` 同 `x == 0`。
* 原子是常数：为假（`> 0`）→ **这条边不可达**；为真 → 不产生信息。只含接口符号的原子 → 加进守卫（去重，至多 8 个，先进先出）。
* 一边是**局部**（或保值类型转换下的局部）、它的值是区间、另一边是确切值：收窄这个局部的区间（`l < c` → 上界 `≤ c − 1` 等，与原界取更紧的、不可比时留原界）；
  区间变空 → 这条边不可达；上下界相同 → 确切值。标签说的是**上界**的来源（F-12 只看上界）：上界被收窄 → `check`（原标签是代码来源时取两者中较差的），
  只收窄了下界 → 原标签不变（`[0, 255]:data` 经 `k >= 16` 仍是 `data`，不是代码给的界）。

比较的有无符号：值都是 C 值的数学值（无符号的取值本就非负），原子按数学整数写。
**比较的两边都要"忠实"**：常数，或能证明落在它的 C 类型范围内（`Faithful`）。`if (off + len > max) return;` 里 `off + len` 可能回绕（u32 的上界 2^33 − 2），
这个检查本身就可能被绕过——不当守卫、也不收窄（召回优先：这正是一类真实缺陷）。

### 2.2 守卫的使用

* **无符号减法**（SPEC-0014 §2.2）：结果在守卫与形参类型范围下能证明非负（`EntailsLe0(−r)`）时不回绕。`if (ulPos == 0) return;` 之后 `ulPos − 1` 就是 `p1 − 1`。
* **当场证明安全**（A-43 / A-44 的"先用守卫判蕴含"）：`末端上界 − have ≤ 0` 在守卫与类型范围（形参、字段、全局、`ext(·) ≥ 0`）下恒成立（`EntailsLe0`）→ 这次访问安全，
  **不生成 Req**；记进 `FunctionFacts::safe`（S8c 写进判定日志，标签 `SAFE`、原因 `local_entailed`），`Dump=state` 打一行 `safe …`。
  例：`UINT8 aucHist[16] = {0}` 的初始化写（末端 1 ≤ 16）——不再变成入口函数上的账本。常数且越界的（F-11 / F-12）本步仍生成 Req（由求解在调用点判；depth 0 的判定在 S8c）。
* **Req 的守卫**（A-44 前半）：生成 Req 时，带上与它的 `have` / `end` 有公共符号的守卫原子（打印成 `ShowLe0`，如 `p1 >= 1`）。覆盖合并只在守卫相同的 Req 之间做。
* **调用点**（D-25）：记下当前全部守卫，`{cond, bound: check}`（调用点判定时作为调用方的环境守卫，SPEC-0012）。
* **汇合**：守卫取交集（A-15）。

## 3. 对召回与误报的影响

当场证明安全只用一定成立的事实（C 类型给出的取值范围、这条路径上的守卫）；证明不了的照常生成 Req。
守卫只在"访问确实只在这些条件下发生"时成立：条件边的方向由 SPEC-0009 钉死（后继 0 为真）；`!=` 只在能由类型 / 已有守卫推出时才产生原子；
不可达只在原子为常数且为假时判定。收益是精度（LV2-09 的 TN 不再误报），不会把原来能报的漏掉——守卫在调用点代换后判不了时，结论仍是上传或记账。

## 5. 测试

* 单元测试 `InterpTest`：`if (n == 0) return; p[n − 1]`（`end n`、守卫 `p1 >= 1`、不回绕）；`if (i < 16) p[i]`（守卫 `p1 <= 15`）；两边常数且为假的边不可达；
  `!=` 无法推出时不产生原子；汇合时守卫取交集；守卫不同的访问不合并；调用点带守卫；区间局部被收窄。
* lit `engine-check.test` 加入 LV2-09、LV3-03（告警与 `alerts.json` 相同，上传 / 判定 / 入口账本条数与金标准推出的相同）。
* `engine_check.py` 加比较条数：从引擎局部事实推出的上传 / 判定 / 入口账本条数要与从金标准摘要推出的相同（"记账"类用例没有告警，靠条数区分"对了"与"凑巧没报"）。
