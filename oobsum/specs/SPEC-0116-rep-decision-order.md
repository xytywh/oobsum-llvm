# SPEC-0116 `run.py` 挑入口的代表判定与判定在日志里的先后无关

状态：已实现
来源：用户 2026-10-26 在公司用 bxen 跑 67 个用例、`run.py csa --from-workdir`：合计与预期相同（通过 106、需跨TU 2、回退 0），但多了几行"变化"：
LV1-04 TN `SUSPECT:typed_field×2 → SUSPECT:entry_unproven×2`、LV10-04 TN `typed_field×3 → type_range_only×3`；本地模拟 bxen 时变的却是 LV10-01。

## 1. 原因

* 一个入口有几条同标签的判定时，`_entry_actual` 用 `max(按标签强度)` 挑代表——并列时取**日志里的第一条**，显示它的原因。
* 判定在日志里的先后随源文件绝对路径变：函数 / 访问的键里有文件 id（路径的哈希，SPEC-0003），按键排的顺序换个目录就不同。
  实测：同一份用例拷到别的目录跑，LV10-01 TN 的"变化"就没了；公司的路径是 `/usr1/oobsum-llvm`，取到的"第一条"与本地不同。
* 判定的集合没有变（本地 32 位 / 64 位、两个路径逐条核对：只有字段偏移这类真实的布局差异，如 LV10-01 的 `*p0` 末端 8 / 24）。

## 2. 设计

代表判定按 `_rep_key` 取最小：标签强度（强的在前）→ 原因 → 对象 → 末端 → 位置的文件名 + 行列 → 读 / 写。全部与路径、先后无关。
入口的实际、汇合点上的最强判定（SPEC-0048）、账本在可达函数里（SPEC-0047）三处都用它。判定本身、判定日志、判据（通过 / 漏报…）都不变。

## 3. 对召回与误报的影响

无（只改对照工具的显示）。

## 4. 实现位置

`oobsum/cases/run.py`（`_rep_key`、`_entry_actual`、`cmd_csa` 里两处）；`oobsum/cases/csa-baseline.json` 按新的显示重写（有意的：只有 `actual` 文本变了，另补了 `nsus` 字段）。

## 5. 测试

* lit `cases-csa.test`：两条 SUSPECT 正反两种顺序，`_entry_actual` 显示相同。
* `run.py csa`：重写基线前 9 行"变化"都只是 `actual` 文本（判据不变）、回退 0；重写后 0 行"变化"。
* 本地模拟 bxen（x86_64、两个不同路径；i386）读 `--from-workdir`：除跨 TU 的 LV1-07 / LV6-01 外，32 位 0 行"变化"，64 位只剩 LV9-02 一行
  （64 位上 `UINT32` → `size_t` 加宽，多 2 条 `type_range_only` 的 SUSPECT——真实的目标差异，多报不少报），两个路径相同。

## 6. 调试

看某个入口的全部判定：`grep -h '<入口名>' <WorkDir>/decisions/*.jsonl`。

## 7. 对主规格的修订

无（工具）。SPEC-0002 §2.2"入口的实际"补一句：同标签按 `_rep_key` 取，与先后无关。

## 8. 公司侧验证

`git pull` 后对已有的 `/usr1/oobsum-cases-wd` 再跑一次 `run.py csa --from-workdir`（不用重跑 bxen）：除 LV1-07、LV6-01 的"需跨TU"外，只应剩 LV9-02 一行（64 位的真实差异）。

## 9. 待定 / 以后

引擎里"重复访问"取哪条当代表（`dup_of`）也按先后取：换路径时报出的那条的对象文字可能不同（条数、位置不变）。以后需要逐字可复现时再按同样的键排。
