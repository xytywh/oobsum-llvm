01四个决定性发现

按对技术选型的影响排序。前三条是「Infer 确实做到了」，第四条是「但你不能靠它」。

FINDING 01 · 实测数据

摘要里真的写着 requires

BufferOverrun 的摘要主体是一组符号安全条件，真实文本是 buf.offset + i < buf.length。这正是团队想要的 0 <= idx < extent(p)，且能沿调用链逐层代换。

FINDING 02 · 实测数据

200 层调用链，0.76 秒

摘要条数严格等于过程数，峰值内存 178→189 MB。每个过程恰好分析一次。 「把有效深度从 2 层提到十几层」在直线链上已被证实。

FINDING 03 · 源码确认

循环的秘密只有 10 行

Infer 不 unsupported，靠的是标准 widening ＋ 一个技巧： 把比较条件里的常量收进阈值集合，于是 i 外推成 [0,10] 而不是 [0,+∞]。

FINDING 04 · Changelog 源码确认

BufferOverrun 已被官方废弃

v1.3.0 Changelog 将其列入 deprecated，Checker.ml 写着 “Use Pulse instead”。但 Pulse 的 57 个 issue type 没有任何一个是数组越界类，实测 --pulse-only 一条越界都不报。

02Infer 的 Function Summary 到底是什么

不是统一 schema，而是「每种分析各自定义一个可序列化 payload，挂在同一张 SQLite 表的不同列上」。

问题答案证据
数据结构Payloads.t 的 17 个可选字段 ↔ PayloadId.t 的 17 个变体源码确认
存在哪里SQLite infer-out/results.db 的 specs 表，21 列 = 4 固定 + 17 payload实测数据
序列化格式OCaml Marshal 二进制，魔数 0x8495a6be（不是 JSON / Protobuf）实测数据
谁生成Ondemand.analyze_proc_name → run_proc_analysis → Callbacks.iterate_procedure_callbacks源码确认
谁读取Summary.OnDisk.get：两层内存 LRU → SELECT … FROM specs WHERE proc_uid = :k → 惰性反序列化源码确认
怎么组合ConditionSet.subst（形参→实参代换）+ check（判级）+ for_summary（未判定的继续上传）源码确认
跨过程不动点过程内有；过程间默认没有，按需一次性分析即固化源码确认
最大调用深度ondemand_callchain_limit 是可选项，无默认值 = 不限制源码确认
对我们的启示

不要设计一个「万能摘要 Schema」去同时覆盖参数范围、指针偏移、别名、路径约束、副作用。 Infer 自己把 BufferOverrun 都拆成了两个 payload（抽象内存 / 安全条件集合）。 为「内存越界」单独设计一个聚焦的摘要类型，物理上放同一张表的不同列即可。

03逐层代换：把 Summary Composition 看清楚

实测数据 三层调用链，四份真实摘要。这是整份调研最核心的一张表。

// sub.c
int leaf(int *base, int idx) { return base[idx]; }
int mid (int *arr,  int k)   { return leaf(arr, k + 1); }
int top (int *p,    int n)   { return mid (p,   n * 2); }
int caller(void) { int a[10]; return top(a, 7); }   // n=7 → k=14 → idx=15 > 10
过程Safety conditions（infer debug --procedures-summary 原样输出）summary_loads
leafbase.offset + idx < base.length @ sub.c:1:39—
midarr.offset + k + 1 < arr.length @ sub.c:1:39
(k + 1):signed32 @ sub.c:3:35		leaf
topp.offset + 2.n + 1 < p.length @ sub.c:1:39
(2.n + 1):signed32 @ sub.c:3:35
(n × 2):signed32 @ sub.c:5:33		mid
caller{ } ← 全部判定完毕，转为报告top

三件事同时发生，缺一不可：形参被实参代换（base↦arr↦p、idx↦k+1↦2n+1）； 源码位置始终指向 leaf 里那次真正的数组访问（sub.c:1:39）， 所以最终报告能精确归因；非线性项 n × 2 被保留成符号而不是放弃。

04循环为什么不需要 unsupported

实测数据 从 --debug 的逐节点 HTML 里抓到的 widening 真实轨迹。

for (int i = 0; i <= 10; ++i) s += a[i];   // a 只有 10 个元素

node5 (loop head) JOIN     i -> (0)  ⊔  (1)        => i -> [0, 1]
node5 WIDEN(num_iters = 1)  prev [0,0]  next [0,1]  => i -> [0, 9]   ← 不是 +∞，是"阈值"
node5 JOIN                                          => i -> [0, 10]
node5 WIDEN(num_iters = 2)  prev [0,9]  next [0,10] => i -> [0, 10]
node5 [exec NARROWING]                                 Fixpoint reached.

同一节点上的数组始终是：
  a -> (_|_, _|_, { f--746625832-1-1(a) -> offset : 0, size : 10 })
        ↑itv  ↑powloc ↑arrayblk：Allocsite → offset/size

整个循环只访问 loop head 三四次，与真实迭代次数无关。最终 i ∈ [0,10] vs size = 10 → 报 L2（部分重叠）。

[0, 9] 这个数从哪来

源码确认 bufferOverrunDomain.ml:392-398——每当一个值与常量 z 做比较（Prune）， 就把 z-1, z, z+1 加进该值的 widening 阈值集合；widen 时外推到「不小于当前值的最小阈值」。

let itv_thresholds =
  Option.value_map (Itv.get_const y.itv) ~default:x.itv_thresholds ~f:(fun z ->
      x.itv_thresholds
      |> ItvThresholds.add Z.(z - one)
      |> ItvThresholds.add z
      |> ItvThresholds.add Z.(z + one) )
今天就能抄的一条

在「遇到循环就 unsupported」与「widen 到 Top 全丢精度」之间，还有一个成本极低的中间选项： 把分支与循环条件里出现的常量收集为 widening 阈值。不到 10 行，却是 Infer 在循环里 保住「i 恰好到 10 而不是到 +∞」的全部秘密。

全局数组漏报的源码根因 源码确认 实测数据

对照实验一句话说清：带初始化器的全局数组能检出，不带的漏报。

int g_noinit[10];                            /* 试探性定义，无初始化器 */
int g_init[10]   = {1,...,10};
static int g_st_init[10] = {0};

g2.c:5: error: Buffer Overrun L1  Offset: 100 Size: 10.   ← f_init     ✅
g2.c:6: error: Buffer Overrun L1  Offset: 100 Size: 10.   ← f_st_init  ✅
（f_noinit 无任何报告，连一条 safety condition 都没生成）      ❌

根因在 bufferOverrunDomain.ml:2169-2190 的 find_global_array： 它获知全局数组 size 的唯一通道是「该全局的初始化器过程 __infer_globals_initializer_* 的摘要」。C 的试探性定义没有初始化器 ⇒ arrayblk 为 ⊥ ⇒ 连条件都不生成。这不是阈值问题，是内存建模的结构性缺口—— 在这一点上 Infer 弱于我们现有的 CSA。

函数指针漏报的根因 实测数据

// fp = &get; fp(a, 22);  的真实 SIL
node5: *&fp:_fn_(*) = _fun_get
node3: n$0 = *&fp:_fn_(*)
       n$1 = _fun___call_c_function_ptr(n$0:_fn_, &a:int*, 22:int)   ← 不是 Call+Cfun

C 函数指针调用被前端降级成对内建函数 __call_c_function_ptr 的调用， BufferOverrun 未为其建模，整个调用退化为「未知调用」，根本不会去读 get 的摘要。

07路径爆炸：摘要解决了什么，没解决什么

一个对选型极重要、且容易被讲错的结论。

层与层之间：加法，不是乘法

实测数据 每层 4 个分支、共 20 层（理论 4²⁰ ≈ 10¹² 条路径）： BufferOverrun 0.28 s，Pulse 0.52 s。两者都没有爆炸， 因为每层摘要在离开该层时已被压缩。

单个过程内部：Infer 靠「主动丢状态」兜底

源码确认 Pulse.ml:1698-1701 设了两道硬闸门： pulse_max_disjuncts 默认 20、pulse_widen_threshold 默认 3。 超限即丢弃状态做欠近似——代价是漏报。

--pulse-max-disjuncts耗时丢弃的析取状态数摘要析取数
50.29 s48{ 5: 2 }
20（默认）0.31 s152{ 20: 2 }
500.39 s314{ 50: 2 }
2000.59 s856{ 200: 2 }

同一个 4096 路径的函数交给非析取的 BufferOverrun：一次 join 得 Offset: [0, 4095] Size: 10，常数代价且检出。

必须正视的推论

「能不能扛住路径爆炸」主要由抽象域是否析取决定，而不是由「用不用摘要」决定。 Pulse 用了摘要，但因为域是析取的，仍要靠丢状态兜底。 如果我们坚持 CSA 的路径敏感（析取）模型做摘要，爆炸只会从「调用点组合」转移到 「单函数内析取数」，不会消失。

08增量分析：版本级 CI 最可迁移的一块

源码确认 实测数据 机制 = 运行分析时顺带记录「谁读了谁的摘要」的依赖边 → changed_files 驱动传递失效。

实验输出含义
源码完全没变，重跑 Invalidated 0 of 8 · Computed 0 · ondemand_procs_analyzed: 0 摘要跨进程持久化并被真正复用

三个必须知道的工程细节

① 默认 infer analyze 会先 delete_all_specs() 清空摘要—— 只有 --incremental-analysis 或 --continue-analysis 才复用。 ② --incremental-analysis 必须配 --changed-files-index，否则直接报错退出。 ③ 该 index 同时决定「分析哪些文件」：capture 只捕获变更文件没问题， 但 analyze 的 index 要覆盖需要出结论的全部文件。

变更判定不是文件哈希，而是逐过程的 CFG 结构比对 （Procdesc.mark_if_unchanged：逐节点、逐指令比较）——改注释、改同文件里的别的函数都不会触发重算。

10技术路线：四个方案与推荐

方案 A

继续当前 CSA Summary

兼容性最好、学习成本最低，但结构性缺口会让成本持续走高而天花板不变。

方案 B

直接基于 Infer 二次开发

技术可行（§09 已证明），但几十个 CSA Checker 需用 OCaml 重写，且前端是 Clang 21.1.6 与我们的 LLVM 14 fork 不一致。

方案 C · 推荐

借鉴 Infer 重设计 Summary 2.0

Checker 层几乎不动、前端一致、自主可控；吸收被验证过的机制，新建与 CSA 引擎解耦的摘要层。

方案 D

Infer 跨过程 + CSA 规则

不建议。源码与文档层面均未见 Infer 提供跨语言集成接口，自建集成层成本与收益不成正比。

为什么不建议直接用 Infer

阻碍性质
唯一有数组越界能力的 BufferOverrun 已被官方 deprecated，Pulse 未补上替代能力产品风险
全局数组（无初始化器）结构性漏报，弱于我们现有 CSA能力缺口
C 函数指针调用不解析，条件不会被实例化能力缺口
前端是 Meta 定制 Clang 21.1.6，与团队 LLVM 14 fork 不是同一套解析结果工程不一致
摘要磁盘格式是 OCaml Marshal，现有 C++ 工具无法直接消费集成成本
Domain / TransferFunctions / Checker 紧耦合于同一 OCaml 进程与 Sil IR，无跨语言可插拔接口架构约束

关于「CSA 生成摘要 + CSA 消费摘要」是否合理

团队的自我判断基本成立，但要分成两句话说。

不合理的部分：让 CSA 引擎自己在 ExplodedGraph 上做循环 widen/narrow、 跨路径 join、摘要不动点。CSA 的 ProgramState 是路径绑定的， 而摘要要求路径无关、可序列化、可任意实例化——这是两种不兼容的状态生命周期假设。 loop abstraction / join / fixpoint / widening / heap / alias / composition / SCC 这 8 项是 「把路径绑定状态变成路径无关摘要」的结构性必需品，换任何引擎都绕不开。 Infer 的选择恰好印证这一点：它没有在符号执行引擎上加摘要层，而是从零建了 92 个文件的独立抽象解释框架。

合理的部分：用 CSA 做路径级事实采集是对的，而且是相对 Infer 的优势—— Infer 的 BufferOverrun 因为域非析取，拿不到「这条越界只在 flag != 0 时发生」这种路径级信息。

核心原则：CSA 只做它结构上擅长的事，把「跨路径归并 / 跨函数组合 / 不动点」交给一个与 CSA 引擎解耦的新组件。

Loop 怎么办

建议：CSA 只收集事实，不做不动点。 CSA 端对循环只做有限次展开（就是现在的做法），目的不是求循环不变式， 而是采集「下标表达式与循环变量的关系、初值、步长、循环条件里的常量」这些事实； FixpointEngine 端拿这些事实做递推式外推——已知 i₀=0、i_{n+1}=i_n+1、 条件 i≤10，直接得到 i ∈ [0,10]，根本不需要在 ExplodedGraph 上迭代。 识别不了的循环退化为 Top，但仍然产出合法摘要，绝不 unsupported。

一条关于精度上限的重要提醒

不要把 Summary 2.0 的目标定成「精度不低于现有 CSA 规则」——这做不到，摘要的本质就是有损压缩。 正确目标是：在现有规则之外新增一条「跨函数」检出通道，两者并存、各报各的， 用 L1/L2 分级让消费方按等级决定拦不拦。如果硬要求「摘要路径不劣于 inline 路径」，这个项目大概率会失败。

13核心问题结论

十个问题，每条给出明确结论与核心依据。

Q1

Infer 的 Function Summary 本质上是什么？

每种分析各自定义一个可序列化 payload，挂在同一张 SQLite 表的不同列上。 对内存越界最相关的形态是 BufferOverrun 的「安全条件集合」，真实文本形如 buf.offset + i < buf.length。

依据：Payloads.mli / PayloadId.ml 源码 + specs 表实测 schema + 真实摘要 dump。 限制：不存在可照搬到所有规则族的万能格式；磁盘格式是 OCaml Marshal。

Q2

Infer 为什么能处理我们处理不了的 Loop / 复杂 CFG？

因为失败模式是「精度可控降级」而不是「放弃生成摘要」。 标准抽象解释 + widen/narrow + 把比较常量作为 widening 阈值。实测 loop head 只访问三四次即达不动点。

依据：AbstractInterpreter 源码 + 真实 widening 轨迹 + 13 类场景实测。 限制：保证终止不保证精确；case 3 / 13a 默认仍漏报，需调高灵敏度，代价是符号噪声。

Q3

Summary 如何生成、存储、读取和组合？

生成：Call 时 analyze_dependency 按需递归分析。存储：Marshal 写入 specs 表对应列。 读取：两层内存 LRU → SQLite → 惰性反序列化。组合：subst 代换 + check 判级 + for_summary 续传。

依据：ondemand.ml / Summary.ml / CallbackOfChecker.ml 逐函数追踪（含行号）+ 三层代换实测。 限制：全局变量的摘要路径存在结构性缺口。

Q4

是否真的避免了指数级路径爆炸？

层与层之间是；单个过程内部不是。 层间是加法（每层摘要离开时被压缩）；层内 Pulse 有 20 条析取硬上限，超限即丢状态做欠近似。

依据：Pulse.ml 源码 + 丢弃计数实测（48/152/314/856）+ 20×4 分支压力实验。 推论：能否扛住爆炸主要由抽象域是否析取决定，而非用不用摘要。

Q5

分析 10~20 层调用在工程上是否可行？

可行，且余量很大。实测 200 层 0.76 s、摘要数线性、内存几乎不增长； 自写的 MiniOobChecker 同样做到 20 层 0.31 s。默认无最大深度限制。

依据：深度实验表 + MiniOob 深链实验。限制：需在真实业务函数上复测（深链常伴随循环/别名/全局）。

Q6

能否像开发 CSA Checker 一样开发自己的越界规则？

可以，本调研已经做完并跑通。但范式不同：不是挂回调，而是实现 Domain + TransferFunctions + checker 三件套再注册。实测成本 442 行 + 37 行注册，无需改任何 dune。

依据：完整源码 + 真实 diff + 真实运行日志。限制：补成生产级是数量级更大的工作。

Q7

能否只复用框架、自己写 Domain 和 Transfer Function？

在 Infer 内部可以，这是官方唯一推荐方式；把框架抽出来接给 C++/CSA 用不可以。 analyze_dependency 一个回调就封装掉了 Ondemand / SQLite / LRU。

依据：labs 官方 lab 源码 + 本次实现验证。限制：产出只服务「在 Infer 里重做一套」，无法反哺现有 CSA。

Q8

「CSA 生成 + CSA 消费」这条路线是否合理？

部分不合理，团队的自我判断基本成立。 不合理的是让 CSA 引擎自己做摘要的抽象解释——路径绑定状态与路径无关摘要是不兼容的生命周期假设。 合理的是用 CSA 做路径级事实采集，这反而是相对 Infer 的优势。

依据：CSA 状态模型分析 + Infer 另建 92 文件抽象解释框架的事实 + 析取域必须丢状态的实测。 性质：工程判断，非可证明定理。

Q9

最应该借鉴哪 5~10 个机制？

按投入产出比：① 依赖边 + changed_files 传递失效； ② 比较常量→widening 阈值；③ L1/L2/S2/只传不报 的分级告警；④ Payload-per-Analysis； ⑤ 安全条件作为摘要主体 + subst + for_summary；⑥ 含符号/非线性 Bound 的区间域； ⑦ On-Demand + 两层缓存；⑧ 逐过程 CFG 结构比对判断变更；⑨ 库函数模型表；⑩ 独立轻量 FixpointEngine。

另有两条反面借鉴：全局变量必须一等公民建模；C 函数指针需专门建模——这两处 Infer 都有缺口。

Q10

下一阶段最值得投入的技术路线？

方案 C——借鉴 Infer 核心机制、重新设计 CSA Summary 2.0， 同时用官方预编译 Infer 做零成本交叉验证。不建议 B（迁移）、A（维持现状）、D（混合）。

前提：必须接受「摘要通道精度天然低于 inline 通道」，目标是新增一条跨函数检出通道而非取代现有规则。

14风险、未确认项与常见误解澄清

本调研未能确认的事

① 对 extern 声明、在另一 TU 定义的全局数组是否也漏报； ② 高灵敏度配置在真实业务规模上的误报率； ③ Pulse 析取上限调大到多少会在真实代码上不可接受； ④ Infer 在大型真实工程（万级文件）下的端到端耗时与内存—— v2 已补上 compile_commands.json 全量分析的机制验证（见下一节）， 但规模仍是三文件级，真实业务规模的耗时、内存与 capture 成功率必须在你们自己的代码库上测。

本版澄清的常见误解

常见说法本版结论
「Infer 就是 Bi-Abduction」对当前版本不准确：biabduction/ 已整体移除，思想保留在 PulseAbductiveDomain
「Pulse 已取代 BufferOverrun」能力上没有：57 个 issue type 无任何数组越界类，实测一条都不报
「Infer 摘要是统一 schema」不是：17 个 analysis-specific payload
「摘要解决了所有路径爆炸」没有：爆炸从「调用点组合」转移到「单函数内析取数」，靠主动丢状态兜底
「第二次跑会自动复用摘要」默认不会：analyze 会先清空 specs，只有增量模式才复用
「循环里会 widen 到 ±∞」不一定：比较常量成为阈值，实测 [0,1] → [0,9] → [0,10]
两条路都要面对的同一个风险

Infer 自己已经把 BufferOverrun 标成 deprecated，Pulse 又没接上数组越界能力—— 这说明连 Meta 都没有在「工业级 C/C++ 数组越界」这条线上维持长期投入。 决定自建，要接受「这条路上没有可长期跟随的开源参照物」； 决定用 Infer，要接受「你依赖的这条分析随时可能被上游删掉」。

这组数据把 §11 的 P0 优先级往前推了一格。Infer 的区间域与 widening 是成熟的， 但它 4 个漏报里有 3 个（含最常见的 struct 字段数组）都出在 某类基址拿不到 size，而不是算法不够强。

修正后的第一优先级

把「哪些基址能拿到 extent」做全——局部数组、局部/全局 struct 的字段数组、 全局、堆、形参，一个都不能少——排在 SummaryDB 与 AbstractRange 之前。 内存建模的覆盖面比分析算法更决定召回率。

随之新增一条反面借鉴：extent 必须是内存模型的一等属性，在声明处就建立， 不能绑在某个特殊过程（Infer 绑在全局初始化器）的摘要上， 也不能在声明处对聚合类型止步不前。

全部数字可用调研包 07-capability-boundary/run-boundary.sh 一键复现， 60 个语料在 07-capability-boundary/corpus/，建议固化进 CI 做能力回归。

17方案 C 落地设计与工作量v2.3 增补

把 §11 的架构建议细化成可以开工的设计。这一节给三样东西： 一处架构修正、工作量、以及 一个必须先验证的前提。

架构修正：谁是主要事实源

§11 原来建议「CSA 采集路径级事实、FixpointEngine 做外推」。这条要改。 如果主要事实源是 CSA 的 ExplodedGraph，那么 CSA 每一个放弃探索的地方—— 循环块访问次数到顶、路径预算耗尽、inline 深度到顶——都没有事实可采， 于是没有摘要，于是又回到 unsupported： 当前最痛的失败模式会被原封不动继承。

主：独立 AI（对 clang::CFG，非路径敏感）
      「全函数性」是硬约束——任何函数都必须产出合法摘要
      精度不够就降级为 Top，绝不缺席

副：CSA 路径敏感信息
      AI 判出 L2 之后，再去问 CSA「这次访问在什么路径约束下发生」
      结果作为解释与排序依据附在告警上，不参与「有没有摘要」的判定

代价是显式的：AI 的区间域非析取，拿不到路径相关精度。 if (f) i=20; if (!f) a[i]; 会 join 成 L2，而现有 CSA 规则能精确判安全。 这正是「摘要通道精度天然低于 inline 通道」，两条通道并存，各报各的。

v3.6 · 已立项，进入实施阶段

目标已定：支持现有工具因路径爆炸而不支持的跨多层调用越界场景， 立项统计 2–17 层，不设深度上限，验收覆盖到 20 层。 1–2 层现有工具已支持，摘要通道只报更深的（CSA 已知盲区例外，因为现有规则在那儿收不到回调）。

原来这里的「更省的路线」（只把 inline 加深到 4–5 层，15–20 人日）不采用： 它够不到 17 层，而且 inline 每深一层路径数就成倍增长——加深 inline 恰恰是在放大立项要解决的那个问题。 立项前用来判断「值不值得做」的测量（单函数可判定比例、深度分布、unsupported 根因）不再是前置条件； 唯一影响「怎么做」的 A1 已在 fork 上验证成立。

摘要方式受不受层数限制

维度受不受层数影响依据
成本不受每个函数只分析一次，调用点代换被调者的摘要，层间是加法；Infer 200 层 0.76 秒、摘要数 = 函数数 实测数据
精度：线性传递（i+1、2n+1）无损常数合并、非线性项保留为符号；MiniOob 20 层条件长度不变 实测数据
精度：分支合并 / 循环每层区间变宽，会累积L1 可能降为 L2（仍会报，不拦门禁）
精度：调用没建模的外部函数 / 函数指针 / 递归条件在这一层断掉与第几层无关，与链上有没有它有关 → 模型表比「加深度」更重要

一个对我们有利的事实

起点比 Infer 高

CSA 的 RegionStore 天生把结构体字段建模为 FieldRegion 并带完整类型—— 这正是 Infer 缺的那一块（§16 的结构性漏报）。 也就是说在「内存建模覆盖面」这个最决定召回率的维度上，我们的起点比 Infer 高，而不是低。 这是方案 C 成立的一条硬理由，但它依赖假设 A1，必须先验证。

T0-1 进展：A1 成立，同时暴露了三处 CSA 借不上的地方 实测数据 源码确认
