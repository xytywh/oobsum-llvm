> 成立与否会让总量相差约 15%**。
> **v3.4**：T0-1 已测完对象层（fork 8/8 正确，与上游逐行一致），字段层在上游已实测成立，

## 1. 参照物：本次实测到的两个锚点

| 锚点 | 实测 | 说明 |
|---|---|---|
| MiniOobChecker（本包 `03-`） | **442 行 OCaml + 37 行注册，0 行 dune 改动** | 但它是**教学级**：不处理 struct 字段数组、循环、malloc、多级指针 |
| Infer BufferOverrun 全家桶 | `infer/src/bufferoverrun/` **约 9500 行 OCaml**（14 个 .ml） | 工业级，含模型表、多语言适配 |

**我们要做的东西落在两者之间**：比 MiniOob 完整得多（要过附录 D 那张 25 行的能力表），
但比 Infer 窄得多（只做 C、只做越界、不做多语言、不做 Pulse 那套析取域）。

C++ 比 OCaml 啰嗦，行数大约 ×1.5–2。

### 按里程碑切

| 里程碑 | 内容 | 人日 | 验收标准 |
|---|---|---|---|
| **M0 · PoC**<br>"一条链走通" | ExtentModel 只做局部数组 + 局部 struct 字段数组；BoundExpr 只做线性；SummaryGen 只做直线代码（无循环）；DB + Manager + Applier 最小版；消费侧能报 L1 | **15–22** | **3 层调用链上，跨文件报出一条 L1**，等价于本包 demo-project 那个用例 |
| **M1 · 循环** | 阈值 widening + narrowing + WTO | **+18–26** | `for (i=0;i<=10;i++) a[i]` 报 L2；**任何循环都不产生 unsupported** |
| **M2 · 覆盖面** | ExtentModel 21 种形态全覆盖（含 v3.4 新增的 #21）；GlobalEffect；模型表 | **+23–30**（v3.4，原 +22–32） | **通过附录 D 那张 25 行能力表**，且在 struct 字段数组、全局无初始化器两项上**优于 Infer** |
| **M3 · 分级与精确率** | S2/StillOpen 分级；告警指纹；与现有规则去重 | **+15–22** | 在你们的 TN 语料上**误报 0**；TP 召回不低于现有规则 |

### 3.4 合并估算

| 场景 | M0+M1 | 全量（M0–M5） |
|---|---|---|
| **纯人工** | 33–48 人日 | 99–149 人日 |
| **我写代码 + 你 review/集成/调试** | **14–22 人日** | **48–80 人日** |
| 节省 | ~55% | ~45% |

**为什么不是砍 70%**：瓶颈会从"写代码"转移到**"review + 在你们环境里编译调试 + 拿真实数据迭代"**。
后面这部分的绝对时间不太压缩得动，而且随着项目推进占比越来越高
（M0 阶段我能砍 65%，到 M4/M5 只能砍 25% 左右）。

### 3.5 要我写代码的话，需要你提供

按重要性排序：

1. **一个现有 checker 的完整源码**（`.cpp` + `.h` + `Checkers.td` 片段 + `CMakeLists` 片段）——
   让我对齐你们的代码风格、命名约定、注册方式、诊断输出方式。
   有了这个，我产出的代码可以直接编译，而不是"示意代码"。
2. **构建与运行命令**（`bxen` 的完整调用、编译 checker 的 cmake 命令）。
3. **`getStaticSize` / `MemRegion` 相关 API 在你们 fork 里的签名**——
   即 T0-1 的产出。
4. **10–20 个真实业务函数**（脱敏即可），覆盖 struct 字段数组、全局、循环、深调用链。
5. **现有越界告警的一个样例**（含消息格式、bug trace 格式），用于对齐输出。

**给了 1 和 2，我就能产出可编译的代码；只给需求描述，我只能产出示意代码**——
这个差别很大，值得你花半小时准备。

| 风险 | 概率 | 影响 | 缓解 |
|---|---|---|---|
| A1 不成立（`getStaticSize` 对 `FieldRegion` 不正确） | **低**（v3.4：对象层 fork 已验证、字段层上游已验证） | +4 人日 | T0-1b 在 fork 上复核 |

不要等到 M3。**

## 5. 一个更省的选项（值得认真考虑）

如果 T0 测出来 **A4 不成立**（越界基本不跨 ≥3 层调用），那么有一个**便宜一个数量级**的路线：

**不做完整摘要框架，只做"ExtentModel + 现有 inline 深度从 2 提到 4–5"。**

* ExtentModel 是独立价值最高的一块（10–12 人日），
  它同时能**直接提升现有规则的召回率**——因为现有规则也要判断 extent。
* **v3.4 补充**：走这条路时，现有规则是靠 ExprEngine 给出的地址工作的，
  会撞上 T0-1b 发现的 #21 盲区（`p = &a[2]; p[j]` 这类写法 CSA 连地址都没有，checker 根本收不到回调）。
  要么接受这块漏报，要么在 fork 里改 `StoreManager::getLValueElement`，
  让它像 `evalBinOp` 那样把两个下标相加【推断：改动量在几十行以内，1–3 人日含回归】。
  这部分已算进下面的 15–20 人日。
* inline 深度调整是配置级改动。
* 合计 **15–20 人日**，拿到可能 70% 的收益。

**这不是退而求其次，是让数据决定。**
我在报告 §28 推荐方案 C，前提是"深度是主要瓶颈"——
这个前提本身来自你们的自述，**还没有被数据验证过**。
T0-3 / T0-4 就是验证它的。如果验证不通过，**方案 C 应该降级，我会明说。**
